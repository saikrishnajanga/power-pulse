2. P: Purpose and Scope
2.1 Model A: Forecasting and spike detection
•
Train a model that predicts the next hour of household electricity consumption from recent 
history and calendar information.
•
Extend the model recursively to produce a 7-day (168 hours) and a 30-day (720 hours) 
forecast.
•
Flag forecast hours that look like potential spikes compared with the historical behaviour of 
the same hour of day.
•
Present results in an interactive weekly/monthly chart and export them as CSV files.

4.2 Model A: recursive forecast
•
The function generate_forecast(horizon) predicts one hour, appends that prediction to the 
history, then predicts the next hour, repeating for 168 or 720 steps.
•
Predictions are floored at zero.
•
The weekly and monthly forecasts both start from the same last observed data and are 
generated independently.
•
The notebook warns that errors accumulate over long horizons, so the 30-day forecast 
should be treated as an estimate.
4.3 Model A: spike rule
For each hour of day, the notebook computes the historical median and the median absolute 
deviation (MAD). A forecast hour is flagged as a Potential Spike when:
prediction > median + 3 x 1.4826 x MAD
The factor 1.4826 scales MAD to be comparable with a standard deviation, so the rule behaves 
like a robust 3-sigma threshold per hour of day.

6. M: Maintenance, Monitoring and Risks
6.1 Points to verify before relying on the results
Model A: feature timing may differ between training and forecasting. In training, each row's 
features describe the hour before the row's own timestamp, while its target is the hour after. For 
example, lag_1 is 2 hours before the target and hour is the hour of the row, not of the target. In 
generate_forecast, lag_1 is the hour immediately before the predicted hour and hour is the 
predicted hour's own value. If this reading is right, the evaluation scores and the future forecasts 
are produced under slightly different feature definitions. Recommended check: align training 
features with the forecast function, for example by using the target hour's calendar features and 
shifting lags so lag_1 is the hour directly before the target, then re-evaluate.
Model B: possible target leakage. The feature set is every column except the target kWh 
columns and the house label. If the cleaned files include the appliance power columns 
(appliance{i}_w) and their max, min and std columns, these describe the same appliance in the 
same hour as the target and would reveal it. The target appliance's own lag columns are also 
included. Recommended check: print feature_cols for one house and exclude every column 
derived from the target appliance in the current hour; decide deliberately whether the appliance's 
own lags are allowed.
Model B: training scores are in-sample. Random forests fit training data closely, so train MSE 
is usually very low and the MSE ratio can look poor even for reasonable models. The 2.0 cut-off 
is a rule of thumb, not a statistical test.
6.2 Known limitations
•
Recursive forecasting compounds error; the 30-day forecast is much less reliable than the 
7-day forecast.
•
Model A has no weather, holiday, occupancy or tariff inputs, and the month feature cannot 
learn seasonality from less than a year of data.
•
Model A uses a single 80/20 split. A rolling or expanding backtest would give a more 
dependable error estimate.
•
Spike flags are statistical outliers relative to history, not confirmed events, and are not 
validated against actual spikes.
•
Model B trains separate models per appliance with no hyperparameter tuning and a single 
split per house.
•
Model B appliance mappings contain placeholders (for example Unknown_2, Unknown_3, 
Unknown_5, Unknown_7) whose results are hard to interpret.
•
Model B notebook headings mention Google Drive, but the code uses local paths; the 
cleaning function is defined but not called in the run loop.
6.3 Maintenance recommendations
